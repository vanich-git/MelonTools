### Scope

The user-visible defect on Windows: a model started by Local AI never appears in the
gateway's `/v1/models`, the Connections check and the Models page. This lane fixes the
publication path on Windows only; `Windows/**` ownership, with the minimal possible
diff in the already user-modified `local_models.rs`.

### Requirements

- **R1 Publication.** After a confirmed load, the canonical `local/…` alias is in the
  authenticated gateway catalogue, generated by the app (not a hand-written schema),
  with the effective port, upstream id, internal token and bypass.
- **R2 Lifecycle.** Start/stop/restart/crash rewrite publication; a stopped or failed
  model is not left advertised; a lost engine reload is retried; config, catalogue and
  registry errors are visible instead of being swallowed; the gateway started after the
  model still lists it.
- **R3 Connections.** The Local AI card carries a connection check that distinguishes
  running/published, stopped/stale and error states truthfully.
- **R4 Models UI.** Start/stop refresh the model list and the check state.
- **R5 Safety.** No secrets in fixtures; no version, installed-app or unrelated dirty
  file changes.

### Implementation

Publication state machine (`Windows/app/src-tauri/src/local_ai/local_runtime.rs`):

- `RuntimeInner::transition` bumps `revision`; `published_gateway` records the revision
  whose effects reached the engine.
- `PublicationReporter` (`:1455`) tags the last outcome with its revision, refuses to
  let an older revision overwrite a newer one, and now exposes `is_current(rev)` from a
  read-only `Arc<Mutex<RuntimeInner>>` view (`:1482`).
- `request_resync(rev)` (`:1504`) uses `compare_exchange(rev, 0)` so a newer revision
  published in the meantime is not rewritten, while the current one becomes dirty
  again and the 5 s supervisor rewrites the config. This is the recovery for the
  engine startup race confirmed on the parent lane: the engine serves HTTP before its
  config watcher is armed, so the first write can be lost.
- `pending_gateway_revision()` / `mark_gateway_synced(rev)` (`:1760`, `:1765`) keep a
  revision pending until the catalogue is verified, not just until the file is
  written; `mark_gateway_synced` uses `fetch_max`.

Publication driver (`Windows/app/src-tauri/src/local_ai/commands.rs`):

- `publish_attempt` (`:142`) is the publish core, generic over a write hook and a
  read hook. A write failure is reported and the revision stays pending. On success
  the revision is marked synced, then the catalogue is polled; a lost reload
  re-dirties the revision (`request_resync`) and records the user-facing message
  instead of pretending the model is published.
- `sync_gateway_after_transition` (`:204`) is the adapter: it early-returns without a
  pending revision, snapshots settings and expected aliases on the caller thread, and
  spawns the blocking write plus the async poll. Cache invalidation and the Codex
  catalogue refresh happen only when `reporter.is_current(revision)`, so a start/stop
  that raced the poll owns those side effects.
- A `codex_route::sync_catalog` failure is reported as “published, but the Codex
  catalogue could not be updated”, never as a failed publication; with no Codex route
  the success path stays silent (intentional “no route” case).
- The config write moved inside the spawned task, so `sync_gateway_after_transition`
  returning no longer means the file is already on disk. The dirty revision
  (`pending_gateway_revision`, `request_resync`) is what guarantees the eventual
  write; this is the only behavioural change of the extraction.

Registry persistence (`Windows/app/src-tauri/src/local_ai/local_models.rs:1122`):

- `update_model_status` returns `Result<(), String>` instead of discarding
  `save_registry`. A failed `Ready` write aborts the launch with a visible error
  (`local_runtime.rs:2686`); other lifecycle writes log the failure instead of leaving
  a stale status behind. This closes the silent path where a model ran but the
  persisted registry never made it `Ready`, so the catalogue could not include it.

Config generation and the shared engine fixture
(`Windows/app/src-tauri/src/gateway.rs`):

- `write_config` (`:116`) writes a temp file and `fs::rename`s it, matching the
  engine's `Write|Create|Rename` watcher. It is idempotent per generated
  generation (`last_written_config`), so a settings save or catalogue refresh that
  reproduces the same YAML does not trigger a reload storm.
- `write_config_forced` (`:126`) bypasses only the generation check and always
  replaces the file. It exists for explicit Local AI publication: a retry after a
  lost fsnotify reload has byte-identical YAML, and the idempotent path would
  treat it as "nothing changed" and never repair the missing route. The guard is
  still held across compare and replace, and a failed write leaves the cache
  untouched, so the forced path cannot mask errors.
- The shared writer never truncates the live config in place. If the tmp write or
  the atomic rename fails, it removes the tmp file best-effort and returns the
  OS error; the previous config stays intact and the generation is not cached.
  Explicit publication retries the forced write once the handle/share violation
  clears, so a transient failure costs a delayed reload, not a destroyed file.
- `publish_attempt`'s write hook (`local_ai/commands.rs:224`) uses
  `write_config_forced`; `main.rs` settings saves and the catalogue coalescer keep
  `write_config`/`schedule_write_config`, preserving ordinary coalescing.
- `api_keys_yaml_with_local` (`:239`) is the only generator of the local block.
- `tools/fixtures/local-ai-gateway.yaml` is the tracked native fixture, produced by
  this generator with `MELON_LOCAL_AI_FIXTURE`, a `Ready` placeholder model and port
  `59999`; it contains `__MODEL_ID__`, `__LOCAL_TOKEN__`, `__LOCAL_PORT__` placeholders
  only. `generated_gateway_config_matches_the_tracked_engine_fixture` (`:1540`)
  asserts byte equality (trailing newline trimmed), so the fixture cannot drift from
  the app's own output. `write_engine_api_keys_fixture` (`:1555`, ignored) regenerates
  it on purpose.

UI (`Windows/app/ui/`):

- `mt-pages.js:988` renders the Local AI card with the publication error and the
  check button (disabled only while `S.busy.localAiCheck`, guarded for harnesses).
- `mt-actions.js:1387` `localAiConnectionsCheck` compares the gateway catalogue with
  `Ready` models, lower-case `"ready"` (serde spelling), reports missing/stale/stopped,
  fails on `runtime.publicationError` even when the alias is visible, fails on a stale
  served alias while the engine runs, and fails (does not pass) when the local IPC
  call throws. `localAiStart`/`localAiStop` await `modelsLoad`; the runtime poll
  refreshes the list on state changes.
- `mt-redesign-actions.js:177` overrides `checkApi`: it keeps the gateway check and
  adds the same Local AI verdict (publication error, missing, stale, IPC failure), so
  Connections and the global check cannot disagree; the toast is a success only when
  the verdict is green.
- `mt-i18n.js` carries the `localAiCheck*` keys in ru/en.

## REVIEW

Parent REVIEW found three coverage gaps in the first BUILD:

1. `api_keys_yaml` was only exercised through `api_keys_yaml_with_local`, so no test
   proved the `Ready`/`Installed` registry filter reaches the real generator.
2. A stale `Ready` left by a crash was not tested through normalization and the first
   gateway config.
3. The publish core was reachable only through Tauri `State`, leaving the success,
   lost-reload and write-failure paths untested.

Repair1 addresses all three: `gateway::tests::api_keys_yaml_advertises_only_runtime_ready_models`
(`with_test_root` + serialized temp `LOCALAPPDATA`),
`stale_ready_status_is_normalized_before_the_first_gateway_config`, and `publish_attempt`
extracted behind write/read hooks with four async tests.

A second parent read found that both UI checks ignored `runtime.publicationError`,
ignored a stale served alias while the engine was running, and swallowed local IPC
failures; `local-connections-check.js` scenarios 8–10 pin those and the checks now
fail truthfully.

REPAIR2 (user decision, after a parallel change added idempotent/coalesced config
writes): explicit Local AI publication must not be suppressed by the generation
check. The fix is narrow — a public `write_config_forced` plus a `force` flag in the
shared helper, used only by `publish_attempt`'s write hook; ordinary settings and
catalogue writes keep `write_config` and `schedule_write_config`. Regression covers
repeated identical forced replaces for add and for remove, and failure propagation
into the cache. The parallel coalescing work was preserved, not reverted.

The same parent read found one foreign piece in that lane: after a failed rename the
writer fell back to `fs::write(path, …)`, i.e. in-place truncation of the live
config. That violates R5 atomic restore (a partial file while the engine reads it is
worse than a missed reload). Reviewer confirmed the finding; the fallback was
removed, the writer now returns the rename error and leaves the old bytes, the
generation cache is not updated, and the tmp file is cleaned up best-effort.
`publish_attempt`'s retry repairs the transient failure. Regression uses a real
rename failure (destination occupied by a directory with a sentinel file) and
asserts the sentinel survives and no cache entry or tmp file appears. A portability
read then moved the permission-denial half under `cfg(unix)` (on Windows the mode
change is a no-op, so the forced write would succeed and `unwrap_err` would panic);
the occupied-directory rename case stays unconditional and is compiled for Windows
via `cargo xwin check --tests`.

Reviewer isolation: no independent reviewer exists for this lane's diff (depth 1, no
subagents). The parent is the reviewer of record and owns the Chrome smoke; the
inherited root reviewer of the shared spec, `67bdab94-df63-4b90-abb8-7e6d51a02e87`,
is assigned on the parent record. Nothing in this record claims an independent PASS
of the Windows diff; the reviewer's final verdict is expected after the Mac freeze.
