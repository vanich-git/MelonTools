# Local AI — архитектура

Melon Tools 6.0.0 запускает GGUF-модели локально и отдаёт их клиентам через
существующий API-шлюз. Отдельного публичного API у локальных моделей нет.

## Подсистемы

| Компонент | macOS | Windows | Ответственность |
|---|---|---|---|
| Реестр моделей | `LocalModelStore` | `local_ai::local_models` | установленные модели, настройки, состояния |
| Runtime | `LocalInferenceService` | `local_ai::local_runtime` | запуск и остановка `llama-server` |
| Hugging Face | `HuggingFaceService` | `local_ai::huggingface` | поиск, карточки, размеры файлов |
| Загрузки | `LocalDownloadManager` | `local_ai::model_downloads` | скачивание, пауза, возобновление, проверка |
| Оборудование | `LocalHardwareService` | `local_ai::hardware` | backend, память, рекомендации |
| Секреты | Keychain | DPAPI | токен Hugging Face |

## Маршрут запроса

```
клиент → 127.0.0.1:18317/v1 (API-шлюз) → 127.0.0.1:18318/v1 (llama-server)
```

Шлюз остаётся единственной точкой входа. Локальный провайдер объявляется в
`config.yaml` как `api-keys.openai-compatibility` с именем `melon-local-ai`.

Ключевое свойство блока — `proxy-url: "direct"`:

```yaml
api-keys:
  openai-compatibility:
    - name: "melon-local-ai"
      base-url: "http://127.0.0.1:18318/v1"
      keys:
        - api-key: "<session token>"
          proxy-url: "direct"
```

Без `proxy-url: "direct"` глобальный SOCKS5-прокси применяется и к loopback:
прокси отказывает в соединении на `127.0.0.1`, и каждый локальный вызов падает с
транспортной ошибкой.

## Router и жизненный цикл

`llama-server` работает в router-режиме: один процесс обслуживает все
установленные модели и загружает их по требованию.

| Шаг | Что проверяется |
|---|---|
| Start | процесс запущен (`/health`) **и** конкретная модель загружена (`/models` → `loaded`) |
| Stop | генерация операции увеличена, запуск отменён, процесс завершён, состояния сброшены |
| Сбой процесса | `terminationHandler` + периодический мониторинг нормализуют реестр и маршруты шлюза |
| Idle unload | `/models` → `sleeping`/`unloaded` переводит модель обратно в `installed` |

`MainActor` не делает асинхронную функцию атомарной: после каждого `await`
проверяется, что операция всё ещё принадлежит текущему поколению (generation).
Поэтому «Start A → Stop → Start B» не может остановить чужой процесс, а Stop,
отправленный во время загрузки, действительно отменяет запуск.

Готовность модели — это ответ роутера, а не наличие файла: запись в
`/models` появляется только после того, как движок реально загрузил веса.

## Идентификаторы

Локальные модели живут в пространстве `local/<slug>`:

```
local/qwen3.5-2b-bf16
local/unsloth-qwen3.5-2b-bf16        # загрузка из HF: к слагу добавляется автор
local/qwen3.5-2b-bf16-q4_k_m        # коллизия квантования
```

Суффикс добавляется при коллизии, поэтому два варианта одной модели никогда не
делят один API-идентификатор. Идентификатор вычисляется в одном месте
(`uniqueModelID`) и используется импортом, папкой и загрузкой — переименование
отображаемого названия его не меняет.

## Состояния

`not_installed`, `downloading`, `paused`, `verifying`, `installed`, `loading`,
`ready`, `generating`, `unloading`, `error`, `unsupported`.

Живые состояния (`loading`, `ready`, `generating`, `unloading`) не являются
долговечными: при запуске приложения они нормализуются в `installed`, а после
остановки движка реестр очищается. Модель объявляется в `/v1/models` только в
состоянии `ready` — то есть когда роутер действительно её обслуживает.

## Хранение

```
~/Library/Application Support/MelonTools/
├── models/
│   ├── <slug>-<hash8>/          # по каталогу на модель
│   │   └── <file>.gguf
│   └── .staging-<uuid>/         # копия до проверки (GC при старте)
├── downloads/
│   ├── <job-uuid>/              # один job = одна модель (возможно, split)
│   │   ├── <file>.gguf.part
│   │   └── <file>.gguf.part.json
│   └── .staging-<uuid>/
├── runtime/                     # дополнительный runtime package
├── metadata/
│   ├── models.json
│   ├── storage_settings.json
│   ├── models.ini               # preset, который читает router
│   ├── models.ini.applied       # digest preset'а запущенного движка
│   └── backups/6.0.0-<stamp>/   # резервная копия перед миграцией
└── logs/
    └── llama-server.log         # ограничен 4 МиБ, ротация в .log.1
```

Каждый файл лежит в собственном каталоге модели, поэтому два репозитория с
одинаковым `model.gguf` больше не перезаписывают друг друга; на
регистронезависимом APFS это тоже верно. Загрузка собирается в
`downloads/<job>/`, проверяется и только потом публикуется в `models/`:
сначала staging на целевом томе, затем атомарное переименование, и только после
этого запись в реестре. Старый файл не удаляется до успешной публикации нового.

Split-модель считается установленной только при полном наборе `1…N`: набор
`[1,3]` из трёх отвергается, а скачивание шарда тянет за собой весь набор.

Каталог моделей можно перенести во внешнее хранилище. Операции разделены:

- **Подключить** — использовать папку как есть; отсутствующие модели помечаются
  `not_installed`, файлы не копируются и не удаляются;
- **Перенести** — копирование с проверкой, атомарное переключение и удаление
  старых копий только по явному выбору.

Недоступный внешний том больше не подменяется внутренней папкой молча: реестр
сохраняет путь и сообщает, что хранилище недоступно.

## Настройки

Приоритет значений: **запрос клиента → сохранённые настройки модели → значения
движка по умолчанию**. Сохранённые параметры сэмплинга (`temperature`, `top-p`,
`top-k`, `repeat-penalty`, `n-predict`, `seed`) попадают в preset, поэтому
действуют без участия клиента.

Параметры, которые являются аргументами процесса (`ctx-size`, `cache-type-*`,
`n-gpu-layers`, `threads`, `batch-size`, `flash-attn`, `chat-template`), требуют
перезапуска движка. Сохранение настроек не перезапускает его само: интерфейс
показывает, что применено, и предлагает перезапуск отдельной кнопкой.

`--parallel N` передаётся всегда; контекст на слот — `ctx-size / N`, и именно это
значение рекламируется клиентам и в каталоге Codex.

## Метрики и логи

`GET /metrics` требует `?model=<id>`; без параметра router отвечает `400`.
Метрики читаются только для загруженной модели, чтобы опрос не поднимал
выгруженную модель обратно в память.

Вывод движка идёт через ограниченный ring buffer (2000 строк) с батчевыми
обновлениями UI, секреты в строках редактируются, файл ротируется.
